# Decisions and open items

1. **Java version.** Decided: ERP uses Java 27 to match Foundgine Java (`maven.compiler.release=27`). Work is C#-first; ERP is parked until the CRM side is done.
2. **Solution format.** `crm/Crm.slnx` (the .NET 10 default) instead of `Crm.sln`.
3. **Foundgine .NET** is consumed as the single package `Foundgine.Providers` 3.3.3 (net10.0), which brings `Foundgine.Core` and `Foundgine.Runtime` transitively. Until it is on nuget.org it is restored from `nuget-local/` via `nuget.config`; that folder must hold the 3.3.3 `Foundgine.Core`, `.Runtime` and `.Providers` nupkgs.
4. **Foundgine Java** is not yet wired in; no published artifact was supplied, only source (3.3.1).
5. **Foundgine EF/ORM providers** (`Foundgine.Providers.Orm`, `.Orm.Generator`, `.EntityFrameworkCore`) are bundled inside the `Foundgine.Providers` package (3.3.3 onward), together with the AOT and ORM source generators. The earlier vendored copy in `crm/foundgine/` (needed because 3.3.2 did not include them) has been removed.
6. **Schema management.** Plain SQL migrations in `crm/src/Crm.Api/db/migrations/`, applied at startup (`Database:MigrateOnStart`) and tracked in `schema_migrations`. EF migrations are not used because the EF model is generated from the Foundgine model.
7. **Auth in Phase 3** is a dev-only header scheme (`Auth:DevHeaders`, off by default) so tenant and role rules are testable. Phase 2 replaces it with Keycloak JWT; the `tenant_id` claim and role names are already what the services read.
8. **Authorization split.** Role policies (`crm.read`, `crm.write`) guard endpoints; tenant scoping is enforced in the services. Foundgine's semantic authorization policy is allow-all, as in the SupplyChain sample.
9. **UNVERIFIED.** The CRM code has never been compiled: no .NET SDK was available, and the Foundgine SupplyChain sample it follows is itself marked "not compiled yet". Expect to fix compile errors first.
10. **Phase 2 scope.** CRM side only: realm, JWT validation (issuer, audience, lifetime, signature), roles and tenant claims. ERP JWT validation is deferred. Not yet done: secret rotation, workflow-signal authorization, rate limiting (Phase 9).
11. **Realm unverified.** `enterprise-realm.json` is generated, not tested against a running Keycloak 26; unmanaged user attributes are enabled so `tenant_id` imports.
12. **Phase 5/6 scope (C# only).** CRM side of onboarding: mapping table, transactional outbox, outbox publisher (Temporalio .NET client), CRM activities hosted by a .NET worker inside the API process (`Temporal:Enabled`). Not written: the Java `CustomerOnboardingWorkflow`, ERP activities, ERP inbox. `Temporalio` is pinned `[1.7.0,2.0.0)` and the SDK calls are unverified against the real package.
13. **Tenant propagation for workers.** Activities receive `tenantId` in their input and use `IntegrationService` (no HTTP/JWT). Service-account auth for CRM APIs from workers is still open (see keycloak.md).
14. **Phase 7 scope (C# only).** CRM opportunities, quote lifecycle with segregated approval, accept -> outbox -> QuoteToOrderWorkflow start, ERP order recording, customer sales history. Quote approval is a CRM state machine, not yet a Temporal workflow. Quote lines carry SKU only (no ERP product validation yet).
15. **Phase 8 scope (C# only).** CRM mirrors of ERP shipments/invoices/payments (idempotent, version-guarded upserts via `crm.record-*` activities), CRM-owned return requests with outbox -> `ReturnProcessingWorkflow` and `crm.record-return-decision`, read endpoints. See `docs/fulfilment.md`. Not written: any Java workflow or ERP activity, a return reconcile endpoint, customer-visible invoice PDF/download, payment initiation. Like everything C# here it has never been compiled (item 9) and the new SQL (`NULL`-free filters using 0 = any, `RETURNING` via `SqlQuery<int>`, `ANY(int[])`) is unrun against PostgreSQL.
16. **Phase 9 scope (CRM side, partial).** Added: per-tenant fixed-window rate limiting (`RateLimit:PermitsPerMinute`, default 600, 429 on excess; per-IP when unauthenticated), `X-Correlation-Id` middleware (sanitised, echoed, in the logging scope and in audit rows), append-only `admin_audit` (migration 005) written by an endpoint filter on quote approve/reject and integration reconcile, `GET /audit` (admins, tenant-scoped, newest first). Caveats: the audit filter runs after authorization, so role denials (403 by policy) are not audited; audit rows are written on a separate connection, so a failed business transaction is still recorded; the rate limiter is in-process (not shared across replicas). Not done: OpenTelemetry traces/metrics (needs packages not available offline), correlation propagation into Temporal headers, secret rotation, workflow-signal authorization, backup/restore, alerting. Unverified like items 9 and 15.

19. **ERP Java side, second increment (quote-to-order, Phase 7).** ERP: Flyway `V2__erp_orders_inventory.sql` (`erp_products` with a `min_unit_price` floor, `erp_inventory` with CHECKs `reserved <= on_hand`, `sales_orders` unique on tenant + CRM quote, lines, `stock_reservations`, `order_inbox`). `ErpOrderService.createOrderWithReservation` creates the order and reserves stock in one atomic transaction: replay returns the existing Open order and reserves nothing; a cancelled order is refused (never handed back as live); customer must be an Active ERP customer of the tenant matching the CRM id; every SKU must be an active product; a line below the floor is rejected; the quote total must equal the sum of lines; stock is reserved with a conditional `UPDATE ... WHERE on_hand - reserved >= qty` in SKU order, so concurrent orders cannot over-reserve and any failure rolls back the whole order. `cancelOrder` is the compensation (releases the reservation, idempotent). Activities `erp.create-order-with-reservation` / `erp.cancel-order` (non-retryable types `ValidationFailed`, `InsufficientStock`), registered in the ERP worker. Orchestration: `QuoteToOrderWorkflow` (ERP order -> `crm.record-erp-order`; CRM retries are unlimited so a CRM outage is waited out; on a permanent CRM refusal the ERP order is cancelled; query `status`). **Decisions:** price rule is a per-product floor, not exact list price (CRM quotes may carry discounts); an out-of-stock order fails the workflow (Failed, nothing left behind) rather than waiting for stock; on Failed the CRM is told through `crm.mark-order-failed` (item 20). **Verification:** the pure rules (`OrderPlanner`) were compiled and run with javac, and the migrations plus every SQL statement of the service (idempotent insert, conditional reserve, rollback, cancel, 8 concurrent reservers against 10 units -> exactly 5 win) were run in psql on PostgreSQL 16. Not run: the Spring/JdbcClient code (list-parameter expansion for `IN (:skus)`, the `Object[]` row mapper), the Temporal workflow tests and the Spring wiring: no Maven Central access here, so they are unverified like item 18. Not done: tax calculation, ERP product/inventory management endpoints (seed rows by SQL for now), ERP Keycloak JWT, `QuoteApprovalWorkflow`, `OrderCancellationWorkflow` as a user-initiated flow, replenishment, fulfilment/return workflows.
20. **CRM `crm.mark-order-failed` (closes the gap in item 19).** Migration `006_quote_order_failed.sql` adds status `OrderFailed` and `order_failure_reason`. `QuoteService.MarkOrderFailedAsync`: Accepted -> OrderFailed with the (500-char) reason; already OrderFailed is a no-op; Ordered or any other state is a conflict (an ERP order exists, never overwrite it); another tenant's quote is NotFound. `RecordErpOrderAsync` still requires Accepted, so a stray order message cannot revive a failed quote. `QuoteToOrderWorkflow` calls it whenever it ends Failed (ERP refusal, or CRM refusal after ERP compensation), best effort and in a detached scope; a permanent CRM refusal of the report itself is swallowed so the real reason is not hidden. Sales history (Accepted/Ordered only) excludes OrderFailed quotes automatically. **Verification:** migration 006 applied after 001/003 on PostgreSQL 16 and the new constraint checked; the orchestration Java was syntax-checked with javac (only missing-dependency errors, no Temporal/JUnit jars here). The C# (service, activity, two new xUnit tests) is uncompiled like item 9; Java workflow tests unrun like item 18. **Open:** there is no way yet to retry a failed quote (re-approve / reopen); the opportunity stays ClosedWon; no admin endpoint lists OrderFailed quotes (query `quotes WHERE status = 'OrderFailed'`).
21. **ERP Java side, third increment (returns, Phase 8).** ERP: Flyway `V3__erp_returns.sql` (`erp_returns` unique on tenant + CRM return id, `erp_return_lines`, ERP-owned `erp_return_seq`). `ErpReturnService.authorize`: idempotent replay of the stored decision; the order row is locked (`FOR UPDATE`) while returnable quantity (ordered minus other Authorized/Completed returns, per SKU) is computed, so concurrent returns cannot exceed the order; business refusals (unknown order, other customer's order, cancelled order, SKU not on the order, over-quantity) are decision `Rejected` with a note, not failures; a rejected return is stored for replay unless the order is unknown (nothing to reference). `complete`: locks the return, adds the quantities to `on_hand` once (the Authorized -> Completed change gates the stock update), only for Authorized returns. Activities `erp.authorize-return` / `erp.complete-return`. Orchestration: `ReturnProcessingWorkflow` (authorize -> `crm.record-return-decision` Authorized|Rejected -> wait for signal `goodsReceived` up to 30 days -> `erp.complete-return` -> record Completed; query `status`; a malformed request is recorded as Rejected so the CRM return never sticks in Requested; on timeout the return stays Authorized in both systems and the result is `AwaitingGoodsExpired`). **Decisions:** returns are allowed on any Open order (the ERP has no shipments yet, so "delivered" cannot be checked); a permanent CRM refusal of a decision fails the workflow visibly rather than being swallowed. **Verification:** pure rules compiled and run with javac (8 checks); V1-V3 applied on PostgreSQL 16; the authorize/complete statements run in psql, including two concurrent returns of 3 against 5 ordered (exactly one Authorized, one Rejected) and a status-gated stock add (20 -> 23). Not run: Spring/JdbcClient code, the Temporal workflow tests, the JUnit DB tests (no Maven Central here, same as items 18/19); orchestration Java syntax-checked only. **Not done:** credit note / financial adjustment, the goods-received signal sender (no endpoint, and signals carry no identity: workflow-signal authorization is still the Phase 9 gap), an operator path for `AwaitingGoodsExpired`, a CRM return reconcile endpoint.

22. **EF Core everywhere except two row locks.** `Outbox`, `QuoteService`, `IntegrationService`, `CustomerService`, `AdminAudit` and `FulfilmentService` no longer use hand-written SQL. Status changes are version- or status-guarded `ExecuteUpdateAsync` calls (same single-shot semantics as the old conditional UPDATEs); ERP mirror upserts are a guarded `ExecuteUpdate`, then an insert when the row is new, where a concurrent insert loses on the primary key (`23505`) and is ignored; the outbox and audit rows are `OutboxMessage` / `AdminAuditEntry` entities. The row types `MappingRow`, `AuditRow`, `ShipmentRow`, `InvoiceRow`, `PaymentRow`, `ReturnRow`, `ReturnLineRow`, `SkuQuantityRow`, `OutboxRow` are gone; services return the entities. `ReturnStatuses` (with `CanMove`) stays in `Domain/Models.cs`; the request body type was renamed `ReturnRequestInput` because `ReturnRequest` is the entity. **Raw SQL that remains, on purpose:** the outbox claim (`FromSql ... FOR UPDATE SKIP LOCKED`) and the per-quote return lock (`FromSql ... FOR UPDATE`) because EF has no row-lock hint, and the migrator's baselining. API JSON changes slightly: return rows now carry the entity's empty `lines` list and `tenantId`; audit rows carry `tenantId`.

26. **Workflow-signal authorization (goodsReceived).** The ERP is the one authorized sender: `POST /api/v1/returns/{returnId}/goods-received` (`ReturnController`, `@PreAuthorize` `erp-inventory` / `erp-admin` / `enterprise-admin`). Tenant and sender come only from the token (`ErpCaller`): `GoodsReceivedService` looks the return up by tenant (`GoodsReceivedPlanner`: Authorized -> signal, Completed -> no-op 200, unknown/other tenant -> 404, Rejected or expired workflow -> 409, Temporal off -> 503), builds the workflow id from the token tenant and sends `goodsReceived({receivedBy: <subject>})` through `ReturnSignals` (`TemporalReturnSignals`, untyped stub, shared `WorkflowClient` bean now exposed by `TemporalWorkerConfig`). `ReturnProcessingWorkflowImpl` ignores a signal with a blank `receivedBy`. **Decisions:** no dedicated warehouse role was added (`erp-inventory` is the receiving role); the signal names the authenticated subject, not a caller-supplied string. **Limit:** Temporal does not authenticate signal senders, so this closes the application path only; direct access to the Temporal frontend (CLI, any client) can still signal, and must be restricted at the network / mTLS level (not configured here). Signals to the other workflows: none exist. **Verification:** `GoodsReceivedPlanner` and the workflow-id format were compiled and run with javac; the rest was syntax-checked only (no Maven Central, items 18/19/21/25). Unrun: `ReturnControllerTest` (note it sets `ROLE_*` authorities explicitly because `jwt()` bypasses the app's converter), the SQL lookup in `GoodsReceivedService`, `WorkflowNotFoundException` being what a closed workflow signal throws in Temporal 1.27, the Jackson shape of the `Map` payload against `Contracts.GoodsReceived`, and the new `signalWithoutAReceiverIsIgnored` workflow test. **Still open:** tracing interceptor on the Foundgine Temporal client, an operator path for `AwaitingGoodsExpired`, secret rotation, Temporal-level access control.

28. **Shipping consumes reserved stock (Checkpoint 16).** Flyway `V6__reservation_consumed.sql` adds `stock_reservations.consumed` with a CHECK that a reservation is never both released and consumed. `ErpFulfilmentService.transitionShipment` to `Shipped` calls `consumeReservation`: locks the order (must be Open), locks unreleased/unconsumed reservations, runs `UPDATE erp_inventory SET on_hand=on_hand-q, reserved=reserved-q WHERE reserved>=q` per SKU, marks them consumed. `ErpOrderService.cancelOrder` skips consumed rows. **Decisions:** consume at `Shipped` (goods leave), not `Packed`; shipments are whole-order; cancelling a shipment after `Shipped` does not restock (returns do). **Verification:** NOT RUN here (no PostgreSQL, jq, Maven or Docker in this sandbox): `scripts/stock-consumption-check.sh` (added to the CI outbox-sql job), five new JUnit tests in `ErpFulfilmentServiceTest`, and the e2e selftest. Only syntax checks (bash -n, py_compile, YAML parse) and a javac pass filtered for missing-dependency errors were done. **Not done:** partial/per-line shipments.
29. **CRM database moves to SQL Server (Checkpoint 17, increment 1).** The CRM keeps EF Core through the Foundgine EF provider (`AddFoundgineEf` + `FoundgineDbContext`); only the database provider changes: `Microsoft.EntityFrameworkCore.SqlServer` replaces Npgsql, `CrmEf.UseCrmSqlServer` (with `EnableRetryOnFailure`) replaces `UseCrmNpgsql`. `tools/gen_migration.py` now emits SQL Server types (nvarchar, datetime2, bit, decimal, `SqlServer:Identity`) and the InitialCrm migration, Designer and snapshot were regenerated from it. **Ported Postgres-isms:** `jsonb` -> `nvarchar(max)`; `now()` -> `SYSUTCDATETIME()`; outbox claim `FOR UPDATE SKIP LOCKED` -> `WITH (UPDLOCK, READPAST, ROWLOCK)` + `TOP`; the quote row lock in `FulfilmentService` -> `WITH (UPDLOCK, ROWLOCK)`; `ILike` -> `EF.Functions.Like` with an escape character (SQL Server's default collation is case-insensitive); the `lower(email)` unique index -> a plain unique index (same collation reason); SQLSTATE 23505 -> `DbErrors.IsUniqueViolation` (SqlException 2601/2627). **Removed:** the legacy-script baselining in `DatabaseMigrator` (it only applied to old PostgreSQL databases; SQL Server starts fresh) - `MigrateAsync` also creates the `crm` database, so setup is `./start.sh` and run. Existing PostgreSQL CRM data is NOT migrated (dev data only). Compose: `crm-db` is `mssql/server:2022-latest` on 1433 (sa password must meet SQL Server complexity: default `Crm_dev_pw1!`; an old `.env` with `crm_dev_pw` must be updated). **Verification: NONE of this was built or run** (no .NET SDK, SQL Server or Docker here); only the generator ran and YAML parsed. Check first: `dotnet build`, `dotnet ef migrations has-pending-model-changes`, then the CRM tests against SQL Server.
30. **ERP data access moves to Spring Data JPA on PostgreSQL (Checkpoint 17, increment 2, partial).** `spring-boot-starter-jdbc` is replaced by `spring-boot-starter-data-jpa` (Hibernate); `spring.jpa.hibernate.ddl-auto=validate` (Flyway still owns the schema, Hibernate only checks that entities match it), `open-in-view=false`. **Converted:** customers (`ErpCustomer`, `ErpCustomerRepository`, `ErpCustomerService`), inventory (`ErpProduct`, `ErpInventory`, repositories, `ErpInventoryService`) and orders (`SalesOrder`, `SalesOrderLine`, `StockReservation`, repositories, `ErpOrderService` including `cancelOrder`, which locks the order with `PESSIMISTIC_WRITE`, releases only unreleased/unconsumed reservations and cancels through the entity). **Kept as native queries on the repositories, on purpose:** insert-if-absent (`ON CONFLICT DO NOTHING`) for customers, orders and the inbox tables, and `nextval` for the ERP-owned id sequences: a JPA `save()` that loses a race raises a unique violation and aborts the PostgreSQL transaction, which would break the idempotent replay the sagas rely on. The conditional stock reservation (`reserved + qty WHERE on_hand - reserved >= qty`) is a JPQL `@Modifying` update, so over-reservation stays impossible under races. **Still on JdbcClient (next increments):** `ErpFulfilmentService` (shipments, invoices, payments, stock consumption), `ErpReturnService`, `GoodsReceivedService`, `ExpiredReturnService`, `ErpTemporalEventOutbox`, `TemporalFulfilmentEventPublisher`. Mixed use is safe because JpaTransactionManager shares its JDBC connection with JdbcClient; each service keeps to one style. Tests: `ErpTestSupport` wires repositories, services and a JpaTransactionManager by hand (no Spring Boot) for the ERP_TEST_JDBC tests. **Foundgine Java is NOT wired in:** no Foundgine Java artifact or source is in this repository (decision 4), so this is plain Spring Data JPA. **Verification: NONE.** No Maven, Spring or Hibernate jars here; only a javac syntax pass (no syntax errors; missing-dependency errors ignored). Expect first-compile fixes (Hibernate `validate` type mismatches, repository method names).
